---
description: "结合代码现状起草一条格式化的 Gitee issue 并新建（提交前先确认）"
allowed-tools: Bash, Read, Grep, Glob, TaskCreate, TaskUpdate
---

用户给的是**线索**（一句话需求 / 想法 / 问题），不是标题原文。**先把线索落到代码上**，再写一条有依据的 issue。

## 1. 摸现状

- 从线索里抽出关键词（功能名、界面元素、技术点），用 Grep / Glob / Read 在仓库里定位相关代码。
- 线索含糊或涉及面宽时先派 Explore 摸一遍，弄清：现在是什么行为、相关文件在哪、有没有已存在的近似实现。
- 有疑问（期望行为不明确、多种做法都行）就**问用户**，别自己替用户决定需求。

## 2. 起草 issue

标题统一成 `[模块] 动词 + 对象 [+ 限定]` 的格式：

- **模块**：先用第 1 步摸到的落点定归属，取仓库里已有的说法（终端 / 编辑器 / 文件树 / 侧栏 / 右栏 / git / 智能体 / 设置 / 窗口 等），读代码确认别硬套。
- **动词 + 对象**：动词开头，一句话说清做什么（添加 / 修复 / 支持 / 重构 / 优化）。不照抄用户原话的啰嗦说法。
- **限定**：跨平台、并发、性能这类约束用「，」接在后面（如「，兼容 Windows / macOS / Linux」）。
- 整体压在一行内，**不要**把正文的分节标题搬进标题，也不要用「问题」「bug」这类空词。

例：线索「终端添加关闭tab快捷键，兼容不同OS」→ 标题 `[终端] 添加关闭标签页的快捷键，兼容三端`。

正文按 markdown 分节，**只写有内容的小节**，没有的别硬凑：

```
## 背景

当前行为是什么、为什么需要改（贴关键文件路径 / 行号增强可定位性）。

## 期望

改完之后应该是什么样，可验收的行为描述。

## 实现要点（可选）

排查时发现的落点：相关文件、已知坑、跨平台差异、需要同步改的地方（配色三处、设置项五处等）。

## 验收

怎么验证这条做完了（跑什么命令、界面怎么点）。
```

- 判断/结论必须**基于实际读到的代码**，不许凭印象编；引用了文件就带路径。
- 确实摸不到相关代码时，老实写明「实现待定」，不要编造实现细节。

## 3. 确认后提交

**把「标题 + 正文」原样给用户确认一次**，确认后再往下跑；用户明确说「直接建 / 不用确认」才跳过。

用 Bash 工具跑（**不传 `-R`**，仓库跟着当前目录的 git remote 推断）：

```bash
gitee issue create -t "<标题>" -b "<正文>" -j
```

然后：

- 标题/正文里可能含引号、换行或特殊字符，用单引号、`$'...'` 或把内容塞进变量再传，别让 shell 吃掉字符。
- 从返回的 JSON 取 `number` / `html_url` 报告给用户——新建了哪条、链接是什么。
- 命令失败（没装 / 没登录 / 缺 scope / 不在 git 仓库 / 网络）**原样贴出错误**，不要自己编内容，也不要退回网页操作。
- 只做新建：不改标签、指派、状态等任何其它内容，除非用户在这条命令里明确要求并确认。
